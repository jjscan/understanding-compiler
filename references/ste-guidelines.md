# STE 정규화 지침 (Claim Parser + Language Normalizer)

ASD-STE100(Simplified Technical English)은 항공 정비 문서에서 오독을 줄이려고 만든 통제 언어다.
이 스킬은 STE를 **준수**하지 않는다 — STE의 원칙을 **참고**해 검토 가능한 문장을 만든다.
공식 사전은 신청해야 받을 수 있으므로, 모델이 기억하는 "STE 규칙"을 지어내지 않는다. 아래 규칙만 쓴다.

카파시는 게시물에서 ASD-STE100로 설명을 요청하고, 너무 엄격할 때 “80% 정도”로 완화해 본다고 제안했다.
이 비율은 규칙 준수율이나 검증 점수가 아니다. 이 스킬은 **원문 의미를 보존하는 범위에서 STE의 명료성을 적용**한다.

카파시 제안의 흐름은 글 → 그림 → HTML → 맞춤 설명 영상이다. STE는 Claim 분해에만 쓰는 것이 아니라
사용자가 실제로 읽는 요약·본문·절차 설명의 기초다. 표현 형식은 이해에 맞게 고르며 영상은 현재 스토리보드까지만 지원한다.

근거: [카파시 게시물](https://x.com/karpathy/status/2105819303471976479),
[공식 STE 설명](https://www.asd-ste100.org/about_STE.html), [공식 FAQ](https://www.asd-ste100.org/STE_faq.html).
카파시 본문은 저장된 `understanding/karpathy-understanding-llm-outputs/source.md` 전사본으로 대조했다.
이번 점검에서 X 직접 조회는 실패했다. 첨부 이미지의 규칙 목록은 공식 표준 전체를 대신하지 않는다.

## 1. 분해 규칙 (Claim Parser)

1. **한 Claim = 한 의미.** 접속(하고, 하며, 이고, 그리고, and), 이유(때문에, 므로, 덕분에), 목적(위해)을 만나면 쪼갤 수 있는지 본다.
2. **평가는 항상 따로.** 사실 + 평가가 섞이면 평가 부분을 `opinion` Claim으로 분리한다.
3. **인과는 항상 따로.** "A 때문에 B" → `A`(fact) / `B`(fact) / `A가 B의 원인이다`(causal). 원문이 인과를 말할 때만 세 번째 Claim을 만든다.
4. **조건을 떼어내지 않는다.** "X일 때 Y" 는 하나의 `conditional` Claim으로 둔다. 조건 없이 Y만 남기면 의미가 바뀐다.
5. 쪼갠 Claim들은 같은 `source_text`를 공유해도 된다. 한 Claim에 `compound-split` 플래그를 단다.
6. 원문이 같은 주장을 반복하면 Claim은 한 번만 만들고, 처음 나온 위치를 `source_location`으로 한다. 반복 위치는 `notes`에 적는다.
   **예외 — 절차 단계로 반복될 때:** 구성요소 설명("Worker는 초안을 만든다")이 처리 흐름의 한 단계("4. executor가 초안 답변을 만든다")로 다시 나오면, 단계 쪽은 *순서 속의 위치*라는 다른 정보를 담는다. 단계마다 `procedure` Claim을 따로 만들고 `dependencies`로 설명 Claim을 가리킨다.
7. 원문 순서를 실행 순서로 바꾸지 않는다. `source.units[].ordered: true`(번호 목록)이거나 원문이 "먼저/다음/그 뒤"를 쓸 때만 `procedure`의 순서로 본다. 글머리표 목록은 나열일 뿐이다. 단계 번호("1단계")는 Claim 문장에 넣지 않는다 — 순서는 `flow` visual이 표현한다.
8. 문서 성격을 알리는 고지문("가상의 예시", "수치는 실제 통계가 아님", "초안")은 독자의 신뢰 판단을 바꾸면 Claim으로 만들고(`fact`, `importance: core`), 그렇지 않으면 `coverage.skipped`에 이유를 적는다.

예:
```
원문: Claude Code는 파일을 읽고 수정하며 서브에이전트를 사용하기 때문에 복잡한 프로젝트에 적합하다.

C01 Claude Code는 파일을 읽을 수 있다.                [fact]
C02 Claude Code는 파일을 수정할 수 있다.              [fact]
C03 Claude Code는 Sub-agent를 사용할 수 있다.         [fact]
C04 Claude Code는 복잡한 프로젝트에 적합하다.          [opinion]   ← 평가 분리
C05 C01~C03의 기능이 C04의 이유다.                    [causal]    ← 원문이 "때문에"로 말함
```
C05처럼 다른 Claim을 가리키는 Claim은 `dependencies: [C01, C02, C03]`를 단다.

## 2. 문장 규칙 (Language Normalizer)

| # | 규칙 | 나쁜 예 → 좋은 예 |
|---|---|---|
| 1 | 문장을 짧게 쓴다(서술 25어절, 절차 20어절 이하 권장) | — |
| 2 | 한 문장에 한 주장 | 위 §1 |
| 3 | 주어를 생략하지 않는다 | "위임할 수 있다" → "Main Agent는 Task를 Sub-agent에게 위임할 수 있다" |
| 4 | **같은 대상은 같은 이름** | worker / agent / executor 혼용 → `entities[]`의 대표 이름 하나 |
| 5 | 대명사를 줄인다 | "이는 비용을 줄인다" → "캐시 계층은 비용을 줄인다" |
| 6 | 추상어보다 구체 명사 | "성능 이슈" → "응답 지연" (원문이 구체화했을 때만) |
| 7 | 조건·예외를 생략하지 않는다 | "업로드가 거부된다" → "파일이 1 MB를 넘으면 업로드가 거부된다" |
| 8 | 숫자와 단위를 보존한다 | "약 30%" 를 "30%"로 바꾸지 않는다 — "약"도 보존 |
| 9 | 가능성과 사실을 구분한다 | "줄일 수 있다"를 "줄인다"로 바꾸지 않는다 |
| 10 | 인과와 상관을 구분한다 | "함께 늘었다"를 "때문에 늘었다"로 바꾸지 않는다 |
| 11 | 능동태를 우선한다 | 행위자가 원문에 있을 때만. 없으면 지어내지 않는다 |
| 12 | 원문 용어를 보존한다 | 고유 명사·제품명·API 이름은 번역하거나 바꾸지 않는다 |

**6번과 11번의 한계:** 원문에 없는 구체 명사·행위자를 채워 넣으면 새 사실을 만든 것이다. 원문이 모호하면 모호한 채로 두고 `vague` 플래그를 단다.

## 3. 이름 통일 (naming problem)

참고 링크에서 가장 많이 공감받은 실패 사례: 한 문서가 같은 구성요소를 worker, agent, executor로 번갈아 부르면 독자는 구성요소가 하나인지 셋인지 알 수 없다.

절차:
1. 원문에서 시스템 구성요소·행위자·데이터 이름을 모두 모은다.
2. 원문이 **같은 대상임을 명시하거나 문맥상 확정**되면 하나의 entity로 묶고 대표 이름을 정한다. 대표 이름은 원문에서 가장 먼저/자주 쓰인 이름.
3. 확정할 수 없으면 묶지 않는다. 대신 관련 Claim에 `naming-drift` 플래그와 `review_note: "worker와 executor가 같은 구성요소인지 원문에서 확인되지 않음"`을 단다. 이것 자체가 사람이 검토해야 할 지점이다.
4. Claim `text`에서는 대표 이름만 쓴다. `source_text`는 원문 그대로 둔다.

## 4. 자가 점검 (validate-claims.py가 일부를 경고로 잡는다)

- [ ] `text`에 원문에 없는 숫자가 있는가? → error
- [ ] `source_text`가 해당 단위에 그대로 있는가? → error
- [ ] 원문 구간에 유보 표현이 있는데 `text`에서 사라졌는가? → warning
- [ ] 문장이 둘 이상인가 / 25어절을 넘는가 / 대명사로 시작하는가 / 접속어로 두 주장을 잇는가? → warning
- [ ] 대표 이름 대신 alias를 썼는가? → warning


## 5. 사용자에게 보이는 설명에 적용

- Claim뿐 아니라 summary와 narrative에도 적용한다. 인용문(source_text·example quote)은 고쳐 쓰지 않는다.
- 영어의 절차는 20, 설명은 25 이하를 공백 기준 휴리스틱으로 경고한다. 공식 STE 단어 계수와 다를 수 있다.
- 한국어의 20/25어절은 이 프로젝트의 편집 기준이다. 영어 표준을 준수했다는 판정이 아니다.
- 절차는 한 문장에 한 지시를 우선한다. 조건·예외·동시 행동을 잘못 분리하면 의미가 바뀌므로 사람/모델 검토를 남긴다.
- 문단은 한 주제씩 구성하고 복잡한 설명은 목록으로 나눈다. 설명 text 블록이 6문장을 넘으면 경고한다.
- 능동태와 직접 표현을 우선하지만 행위자·확실성·시간 정보를 원문 밖에서 추가하지 않는다.
- 영어의 utilize/commence/prior to/in order to는 쉬운 대체 표현을 제안한다. 공식 사전 판정이나 자동 치환이 아니다.
- 기술 명사·API·제품 이름을 보존한다. 단어의 의미·품사·명사구 길이는 공식 사전과 문맥이 필요하므로 자동 인증하지 않는다.
- 80% 적용 점수, STE PASS, 공식 준수 배지를 만들지 않는다. 결과에는 작성 원칙과 미검증 범위를 표시한다.

예: 가상의 원문이 “The operator may utilize the controller prior to starting the pump.”라면,
“The operator may use the controller before starting the pump.”처럼 단어를 쉽게 바꿀 수 있다.
`may`는 보존해야 한다. 이 예시는 쉬운 표현 원칙의 예이며 공식 STE 준수 문장이라는 판정은 아니다.
