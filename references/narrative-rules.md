# 읽기 페이지 작성 규칙 (`narrative` · `context`)

[7] 단계에서 읽는다. viewer.html은 **읽기 페이지**가 기본 화면이고, Claim 카드·필터·Gate는 **검토 모드**로 물러나 있다.
읽기 페이지의 목적은 하나다 — **원문을 읽지 않은 사람이 이 페이지만으로 "무슨 이야기인지" 이해하는 것.**
그러면서도 문장 하나하나가 원문 Claim으로 돌아갈 수 있어야 한다. 이해와 추적을 동시에 만족시키는 것이 이 계층의 일이다.

---

## 1. 구조

```json
"narrative": {
  "headline": {"text": "…", "claims": ["C01", "C25"]},
  "sections": [
    {"id": "N01", "title": "무엇이 문제인가", "blocks": [
      {"kind": "text",   "sentences": [{"text": "…", "claims": ["C01"]}, {"text": "…", "context": ["K01"]}]},
      {"kind": "visual", "ref": "V01", "caption": "작성자가 제시한 형식 사다리"},
      {"kind": "points", "sentences": [{"text": "…", "claims": ["C10"]}]}
    ]}
  ]
},
"context": [
  {"id": "K01", "term": "ASD-STE100", "text": "…", "reason": "원문은 이 용어를 설명 없이 쓴다."}
]
```

| 요소 | 쓰는 법 |
|---|---|
| `headline` | 이 글이 말하는 것 한두 문장. 누구의 주장인지 드러낸다("작성자는 ~라고 본다") |
| `sections` | 3~6개. 원문 논리 흐름을 따른다. 제목은 쉬운 말(질문형도 좋다) |
| `text` 블록 | 문단. 문장 2~5개 |
| `points` 블록 | 병렬 항목(단계가 아닌 나열) |
| `visual` 블록 | 그 그림·표가 설명하는 문장 **바로 뒤**에 둔다. 그림만 따로 모아 두지 않는다 |
| `example` 블록 | 원문의 예시·프롬프트·고쳐 쓰기 전후를 **그대로 인용**. `{"kind":"example","label":"따라 해보기","items":[{"quote":"…","label":"…","claims":["C07"]}]}` — 인용문은 원문에 글자 그대로 있어야 한다(검증기 확인) |
| `callout` 블록 | 섹션의 핵심 한 문장. 섹션당 0~1개 |
| `context` | 원문 밖 배경 설명. 아래 §3 |
| 문장의 `inferences` | 이 스킬이 덧붙인 해석(I..). 주황 바탕 + "해석" 위첨자로 구분된다. 아래 §2-1 |

---

## 2. 문장 규칙

1. **모든 문장은 근거를 가진다** — `claims`(원문 주장) 또는 `context`(원문 밖 배경) 중 하나 이상. 둘을 한 문장에 섞지 않는다.
2. **쉬운 말로 다시 쓰되 강도를 바꾸지 않는다.**
   - 의견은 귀속시킨다: "다이어그램이 더 낫다"(✗) → "작성자는 다이어그램이 더 낫다고 본다"(○)
   - 원문이 유보했으면 유보한다: "쉬울 수 있다"를 "쉽다"로 바꾸지 않는다.
   - 근거 없는 단정은 단정한 사람을 밝힌다: "작성자는 ~가 작동하기 시작했다고 말한다."
3. **연결어도 주장이다.** "그래서·때문에·따라서"는 근거 Claim에 `causal`이 있을 때만. "더 낫다·반면"은 `comparison` Claim이 있을 때만. 나열("또", "한편")은 자유.
4. **새 숫자 금지.** 근거 Claim(또는 context)에 있는 숫자만.
5. **본문은 원문의 이야기를 충실히 전한다.** 의심과 비판은 본문에 섞지 않는다 — "이 글을 믿기 전에 확인할 것"(REVIEW FIRST)과 문장의 점선 표시가 자동으로 맡는다. 본문이 원문을 반박하기 시작하면 독자는 원문이 무슨 말을 했는지 알 수 없게 된다.
6. **핵심(`importance: core`) Claim은 모두 본문에 등장한다.** 빠지면 검증기가 경고한다.
7. 순서를 바꿔도 된다(원문이 결론을 끝에 두었으면 headline으로 올리는 식). 단 순서를 바꾸면서 원문에 없는 논리 관계를 만들지 않는다.
8. **분량은 원문 길이가 아니라 이해에 필요한 깊이로 정한다.** 짧고 압축된 원문(SNS 글, 요약, 슬라이드)일수록 풀어 써야 할 것이 많다. 아래 §2-1의 깊이 기준을 채운다.
9. **개수를 세어 넣지 않는다.** "네 가지 형식", "다섯 구성 요소"처럼 원문이 말하지 않은 개수는 쓰지 않는다 — 항목을 나열하면 된다. 세다가 틀리기 쉽고, 틀린 개수는 새 사실이다.
10. **충돌(conflicting) Claim은 원문대로 단정해서 전한다.** 충돌은 원문이 유보한 것이 아니라 다른 Claim과 어긋난 것이다. 본문에서 "충돌한다"고 논평하지 않는다 — 점선 표시와 "믿기 전에 확인할 것"이 알린다.
11. 문서 성격 고지(가상 예시·초안·버전)를 본문에 쓰려면 먼저 그 고지가 Claim이어야 한다. 제목에 담긴 "v0.3 초안"도 독자 신뢰에 영향을 주면 Claim으로 만든다.
12. 의도한 경고가 남으면 그 문장에 `"note"`로 이유를 적는다 — gate-report의 경고 메시지 옆에 붙는다.

## 2-1. 깊이 기준 — "부실한 설명"을 막는다

원문 문장을 한 줄씩 다시 쓰기만 하면 원문보다 나을 것이 없다. 독자와 목적에 따라 필요한 층만 선택한다. quick은 핵심 질문에 집중하고 standard/deep은 필요한 배경·예시를 확장한다. 근거 종류가 다르므로 섞지 말고 문장·블록을 나눈다.

| 층 | 무엇 | 근거 |
|---|---|---|
| 1. 말한 것 | 원문이 실제로 한 말 | `claims` |
| 2. 뜻 | 낯선 용어·약어·고유명사 풀이 | `context` |
| 3. 예시 | 원문의 예시를 그대로 인용. 원문(이미지 포함)에 있으면 반드시 쓴다 | `example` 블록 |
| 4. 써먹는 법 | 원문의 절차·프롬프트를 "따라 해보기"로 모은다 | `example` 블록 (`label: "따라 해보기"`) |
| 5. 왜 중요한가·서로 어떻게 이어지나 | 원문이 말하지 않은 연결·함의 | 문장의 `inferences` → `inferences[]`(INTERPRETATION) |

- 원문에 표·도표·이미지 속 자료가 있으면 `visual`로 다시 보여 주고 본문에서 그 내용을 풀어 설명한다. 이미지를 "있었다"고만 쓰고 넘어가지 않는다.
- 해석(5층)은 섹션당 1~2문장. 해석이 원문보다 길어지면 그것은 이해 페이지가 아니라 논평이다.
- 의심할 곳은 쓰지 않아도 된다 — 렌더러가 섹션 끝에 "이 부분에서 확인할 것"을 자동으로 붙인다(REVIEW FIRST 중 그 섹션이 기댄 Claim).
- standard/deep에서는 detail이 아닌 Claim의 80% 미만이 본문에 등장하면 경고한다. quick은 이 분량 경고를 생략하지만 핵심 Claim 누락 경고와 전체 추적 검사는 유지한다.

## 3. 배경 설명 (`context`, CONTEXT)

원문이 설명 없이 쓰는 용어·고유명사·전제 지식을 독자가 모르면 이해가 막힌다. 이것을 채우는 곳이 `context`다.
원문 밖 정보이므로 화면에서 **파란 바탕 + "배경" 위첨자**로 원문 내용과 구분되고, 근거 패널에 "CONTEXT · 원문 밖 · AI가 덧붙인 설명"으로 표시된다.

- 넣는 것: 용어 정의, 인물·도구·제품이 무엇인지, 원문이 전제하는 최소한의 배경.
- 넣지 않는 것: 원문 주장의 참·거짓 판정("실제로는 틀렸다"), 원문에 없는 새 논점, 작성자 의도 추측. 판정은 `verification`/`review_note`, 해석은 `inferences[]`의 몫이다.
- 외부 확인을 안 했으면(`meta.external_verification: false`) 널리 알려진 사실만 짧게 쓴다. 확신이 없으면 쓰지 않는다. 확인했으면 `reference`에 출처를 적는다.
- `reason`에 왜 이 배경이 필요한지 한 줄. 쓰이지 않는 context는 검증기가 경고한다.

---

## 3-1. 검증기가 문장마다 보는 것

| 검사 | 등급 |
|---|---|
| 근거(claims/context) 없음 · 없는 ID | error |
| 근거에 없는 숫자(아라비아 숫자) | error |
| 근거에 없는 한국어 개수 표현("다섯 가지") | warning |
| 인과 접속어("그래서·때문에")인데 근거에 causal 없음 / 배경 설명 문장의 인과 표현 | warning |
| 비교·우열 표현("~보다 더 낫다·반면")인데 근거에 comparison 없음 | warning |
| 의견·예측·작성자 추론인데 누구의 주장인지 표현이 없음("작성자는 ~라고 본다") | warning |
| 근거가 uncertain인데 유보 표현 없음 | warning |

## 4. 모드별

| 모드 | narrative |
|---|---|
| `understand` | **필수** (없으면 Gate G2 FAIL) |
| `visualize` | **필수** — visual 블록을 본문 흐름 속에 배치하는 것이 이 모드의 핵심 |
| `inspect` | 선택. 없으면 뷰어가 검토 모드로 열린다 |

## 5. 자가 점검

- [ ] 원문을 모르는 사람이 headline + 섹션 제목만 읽어도 글의 뼈대가 보이는가?
- [ ] 원문을 모르는 사람이 이 페이지만 보고 원문의 방법을 직접 따라 해볼 수 있는가? (따라 해보기)
- [ ] 원문 속 예시·이미지 자료를 빠짐없이 썼는가?
- [ ] 의견·예측 문장이 누구의 것인지 드러나는가?
- [ ] 그림·표가 그것을 설명하는 문단 바로 뒤에 있는가?
- [ ] 원문 밖 설명이 전부 `context`로 분리되어 있는가?
- [ ] 본문이 원문을 반박하거나 평가하고 있지 않은가?


## 설명 기획 예시

```json
"explanation_plan": {
  "audience": "설계를 승인할 담당자",
  "goal": "구성 요소와 승인 전 확인할 조건을 이해한다",
  "opening_question": "이 설계는 사용자 질문을 어떻게 처리하는가?",
  "depth": "quick",
  "questions": [{"question": "어떤 구성 요소가 일을 나누는가?", "claims": ["C01"]}]
}
```

기획은 원문 목차의 복사가 아니라 독자의 질문 순서다. 모든 답은 기존 Claim·Context·Inference에 연결한다.
질문 사이 비약·소개되지 않은 용어·설명 강도는 `reviews.reader_flow`에서 별도로 검토한다.
